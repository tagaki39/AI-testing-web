## 1. 实例身份消歧（下一阶段核心参考）

**关键结论：分而治之——容器内与容器外是两类问题，解法不同。**

### 1.1 容器内重复（Add to cart ×N）

| 环节 | 原项目机制 | 出处 |
|------|-----------|------|
| 生成期 | a11y 树自带 `parent_id` → 构建 `node_by_id` / `children_of` 索引；target 支持 `role="name" inside product "Blue Top"` 语法（`_SCOPE_RE` 只匹配 `inside product "..."`） | `locator_preflight.py:43-46, 362-414` |
| 候选 | 容器内命中生成 scoped 候选：`a11y_scoped_role_exact` 0.95 / fuzzy 0.85 / text_exact 0.70 / text_fuzzy 0.60，携带 `pre_features.scope_name` | `locator_preflight.py:451-464` |
| 执行期 | `get_by_role("product").filter(has=get_by_text(scope_name, exact=True))` 找容器 → 容器内链式查找；兜底：`get_by_text(scope)` 后 `xpath=..` 爬父链（精确 3 层 / 模糊 2 层） | `playwright_runner.py:197-211`、`semantic.py:169-195` |
| Prompt | 容器树格式化：`[container] Blue Top` 容器头 + 子元素缩进 + **重复元素标注 `[duplicate i/N]`**，system prompt 要求 LLM 用 `inside "<container>"` 消歧（prompt 版本 `2026-05-30.product-card-context-v1`） | `dsl_generator.py:535-637, 836-865` |

**对本项目**：✅ 采纳方向——与既定方案（Compiler 从观察到的元素上下文生成 scope）一致。
建议落地顺序：探索采集容器上下文 → Compiler 发现 observation 内不唯一时附加
scope（参考其 scoped 候选分数分层）；`[duplicate i/N]` 标注可先加进 grounded prompt。

### 1.2 容器外元素（View Product 类）——重要情报

原项目实测根因（README:28）：**View Product 链接在 a11y 树中不是产品容器的
child（是独立元素）**——`inside` 消歧对它无效。其解法是 DOM has 链 CSS 兜底：

```css
.product-image-wrapper:has(.productinfo:has-text("Fancy Green Top")) a:has-text("View Product")
```

由 `semantic.py:_resolve_explicit_locator` 或 Tier 0 correction（`css` 类型）执行。

**对本项目**：⚠️ 这解释了我们 automationexercise 6/9 那步必然歧义的根因——
**光做容器内 scope 治不了 View Product**。需要容器外兜底方案（DOM has 链编译 /
corrections 落库 / 或明确拒绝并提示）。方案决策留待实例身份阶段评审时定。

### 1.3 身份证据前移：探索期预验证候选

探索期就在真实页面验证过 `count==1` 的选择器，生成期直接给 `verified_{strategy}`
候选 **pre_score=1.0**（`page_explorer.py:204-214`、`locator_preflight.py:433-447`）。

**对本项目**：✅ 强烈建议采纳——身份证据在探索时固化，而不是执行时现推。
探索时 `_resolve_locator` 成功命中的 target 即可标 verified。

## 2. 评分机制对比（我们的 R2 vs 它的 runtime scoring）

| 维度 | 原项目 | 本项目（R2 已实现） |
|------|--------|---------------------|
| 生成期分数 | pre_score：role 0.90 / fuzzy 0.75 / text 0.55 / scoped 0.95-0.60 / verified 1.0 | 无（编译 target 来自观察元素） |
| 运行期分数 | node_id 130 / role_exact 120 / css 110 / fuzzy 90 / label 85 / **sibling_input 82** / text_exact 80 / placeholder 75 / text_fuzzy 60 | test_id 100 / test_id_attr 95 / role 90 / decorated 80 / text 60 / fuzzy 50 / css 30 |
| 动态加成 | **visible +10 / enabled +5 / preview +3** | 无（可见性只在 dedup 时过滤） |
| 拒绝门槛 | 只有硬性 `count==1` + postcondition 验证，**无 margin 门槛** | **有 margin 门槛（CONFIDENCE_MARGIN=20）+ 放松组** |

**对本项目**：✅ 保持我们的 margin 门槛（它没有，是我们的优势）；
✅ 可借鉴**动态加成**（visible/enabled 作为分数项而非过滤项，融合进 decide_resolution）；
✅ `a11y_label_sibling_input`（label 文本 → 兄弟 input，无名输入框）是值得补的
策略（基础分 82，实现见 `semantic.py:320-353`，含 `__nonexistent__` 优雅失败技巧）。

## 3. corrections 闭环（L1 的完整参照实现 + 一处原则分歧）

**参照实现**（我们 L1 可直接对标）：

- 数据模型（`models/locator_correction.py:24-79`）：`page_url_pattern` /
  `target_description` + `normalized_target_description`（小写+空白折叠）/
  `correction_type`（**限定 css/xpath/test_id 三种**）/ `correction_value` /
  `verified_count` / `consecutive_failures` / `is_active` / 来源执行 id
- URL 泛化（`locators/url_pattern.py:15-28`）：纯数字段 / UUID / ≥16 位
  字母数字混合段 → `*`；query 按 key 排序、动态值 → `*`
- 命中：`generalize_url(当前URL) == pattern AND normalize(target) == normalized
  AND is_active`，按 verified_count 取首条
- 熔断：`consecutive_failures >= 3` → `is_active=False` + `auto_deactivated` 事件；
  成功则 failures 清零 + `tier0_hit` 事件；事件审计表记录每次快照
- upsert：同 pattern+target 已 active → 原地更新 correction_type/value（409 冲突）
- 验证：命中后 `wait_for(visible, 3s)` 才算成功

**⚠️ 原则分歧（保持我们的立场）**：原项目 Tier 0 **绕过** Resolver 评分直接构建
locator（`fallback.py:177-232`）；本项目 ROADMAP 既定原则是
"**correction 是 candidate source，不绕过 Resolver**"——实现 L1 时保持我们的
保守版本（correction 作为最高优先级候选进入解析管线，仍过唯一性/评分/可见性验证）。

## 4. 生成链路增强（质量门 + 自愈重生 + 上下文注入）

原项目 `services/ai_planning.py` 的 generate_drafts 流程（用户重点关注）：

### 4.1 用户上下文注入（`ai_planning.py:641-660`）

生成前组装结构化 user_context：被测系统 / 业务目标 / 核心流程 / 关键断言 /
测试数据 / 范围限制 + **上一次执行的错误上下文**。

**对本项目**：✅ 可借鉴——我们的 generate API 目前只有一段自由文本 prompt；
后续可加可选的结构化字段（不改破坏现有入口），错误上下文注入对应我们的
"失败重试带错误信息"增强。

### 4.2 自愈重生 + anti-pattern 负例（`ai_planning.py:689-713, 935-964`）

- failed draft 下次生成时先删除，错误文本映射 `retry_reason_code`：
  missing_navigation / missing_step / missing_capture_text / invalid_structure
- 以 reason 检索 anti-patterns 作为**负例 few-shot** 注入 DSL prompt
  （`dsl_generator.py:913-937`、`services/anti_patterns.py`）

**对本项目**：✅ 改造采纳——比我们现有的"原输出 + 精简错误"恢复更强。
对应落点：Schema Recovery 失败后的二次恢复，可加入 anti-pattern 负例。

### 4.3 Preflight 质量门（`ai_planning.py:857-889`）

unmatched 比例 > 0.5 或 low 置信度比例 > 0.5 → 草案直接 `status="failed"`，
不产出"看似能用"的 DSL。

**对本项目**：✅ 可采纳——我们的 Preflight 目前对 unresolved 只标 warning；
可加生成期质量门（阈值按我们的指标校准）。

### 4.4 泛化动作名护栏（`locator_preflight.py:40, 92-93, 474-503`）

`_target_is_generic_repeated_action`（add to cart / view product）匹配 >1 →
强制 `locator_confidence="low"` 并提示加产品上下文。

**对本项目**：✅ 采纳——生成期就识别"泛化动作名命中多个"，与我们的
"宁可明确失败"一致。

## 5. VLM Tier 保护（deferred，但设计现成）

`locators/ai_visual.py` 全套保护（将来做 VLM 时直接参照）：

- 断路器：连续失败 ≥3 → 冷却 60s（`_record_failure` / `opened_until`）
- 速率限制：滑动 60s 窗口 / 每分钟 10 次
- 模型降级链：`["glm-4.6v-flash", "glm-4.6v"]`，识别 429 换模型，全失败才计断路器
- 会话级结果缓存（LRU 128，键 = generalize_url + normalize_target），命中仍需
  `wait_for(visible)` 否则失效重查
- 结果置信度 0.35（带 errors）/ 0.7，仅入证据不设阈值
