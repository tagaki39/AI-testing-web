顺着你现在已经走到的位置，我建议你**不要继续优化当前 Locator v1，也不要立刻一次性实现完整“五层 fallback”**。

你现在最好的方向是：

> **把项目从“复杂 Locator Engine”重构成“Grounding Engine + Resolution Engine”两层架构。**

而且要分阶段迁移，不推倒重来。

你当前代码其实已经证明了为什么要这么改：`runner._resolve_locator()` 现在同时负责 scope、等待、候选遍历、visibility、DOM identity、business identity 等多种职责，复杂度已经明显集中在一个 resolver 里。 同时 `ai_agent.py` 还维护 Browser-backed scope inspection、Repair、navigation invariant 等另一套定位相关逻辑。

所以现在不是“再修 Locator”，而是**重新划职责边界**。

---

## 第一阶段：先止血，不重构

你现在那个 5 分钟问题先修掉。

只做：

```text
Resolver global timeout budget
```

因为现在 `count()==0` 后，会在多个 `container × strategy` 上反复等待，导致一次 step 90~110 秒。当前代码确实是在候选循环中逐个 `wait_for()`。

第一阶段验收：

```text
任何 locator resolution ≤ 5s
普通 step 不再出现 60/90/110s
失败也必须 bounded
```

**这一步完成后冻结 Locator v1。**

不要顺手再修：

```text
更多 scope heuristic
更多 icon
更多 business ID
更多 parent crawling
```

---

# 第二阶段：建立 Grounding Engine

这是接下来最值得做的架构变化。

目标：

> **Planner 不再生成 locator。Planner 只选择系统实际观察到的 element ref。**

现在 Planner 还是输出：

```json
{
  "target": {
    "role": "link",
    "name": "Add to cart"
  },
  "scope": {
    "has_text": "Blue Top"
  }
}
```

这意味着模型还在参与构造定位器。

以后改成：

```json
{
  "action": "click",
  "target_ref": "obs7:e42"
}
```

### Observation 新结构

第一版不一定非要马上 CDP。

你甚至可以先基于现在的 A11y observation 做：

```json
{
  "id": "obs7",
  "url": "...",
  "state_hash": "...",
  "elements": [
    {
      "ref": "obs7:e42",
      "role": "link",
      "name": "Add to cart",
      "text_context": [
        "Blue Top",
        "Rs. 500"
      ]
    }
  ]
}
```

然后 Planner：

```text
只能引用系统给出的 ref
禁止创建 role/name/scope
```

这会比 Schema Prompt 再写十条规则更有效。

因为输出空间直接从：

```text
role
name
scope
test_id
text
css
...
```

缩小成：

```text
obs7:e42
```

这和你目前已经在做的 `observation_ref` 思路是一致延伸；你当前系统已经要求 Planner 引用真实 observation ID。

下一步只是把：

```text
observation_ref
```

升级为：

```text
observation_ref + target_ref
```

# 第三阶段：Node Ref → LocatorSpec Compiler

这是架构里最关键的一层。

**Node Ref 不直接成为持久 DSL locator。**

而是：

```text
target_ref
↓
Observation Registry
↓
deterministic compiler
↓
LocatorSpec
```

例如：

```text
obs7:e42
```

系统知道：

```text
role = link
name = Add to cart
context = Blue Top
business id = 1
```

Compiler 决定生成：

```json
{
  "role": "link",
  "name": "Add to cart",
  "exact": true,
  "scope": {
    "has_text": "Blue Top"
  }
}
```

如果以后 CDP 能拿到：

```text
data-testid
data-product-id
DOM attributes
```

Compiler 可以优先生成更稳定的 locator。

重点是：

> **稳定 locator 是代码生成的，不是 LLM 发明的。**

你现在很多 Preflight Repair，其实都是在补救 Planner 的 locator invention。

这一层做好后，Repair 可以大幅缩水。

---

# 第四阶段：新建独立 Resolution Engine

不要继续在 `runner.py` 里扩 `_resolve_locator()`。

新建：

```text
locator/
    model.py
    compiler.py
    semantic.py
    resolver.py
```

公开接口只保留一个：

```python
resolve(
    page,
    locator_spec,
    action,
    timeout_ms,
) -> ResolutionResult
```

返回例如：

```json
{
  "status": "resolved",
  "strategy": "a11y_role_exact",
  "score": 0.96,
  "runner_up_score": 0.61,
  "confidence_margin": 0.35,
  "dom_matches": 2,
  "business_entities": 1
}
```

### 不再把“三分法”当整个算法

而是：

```text
Candidate generation
↓
Scoring
↓
Confidence gate
↓
accept / ambiguous
```

也就是说：

```text
Scoring = 排序机制
Strictness = 是否允许执行的门槛
```

这个区别很重要。

不是：

```text
最高分就点
```

而是：

```text
第一名 0.95
第二名 0.42
→ accept

第一名 0.91
第二名 0.90
→ ambiguous
```

这样你既获得 scoring 的抗变化能力，又保留现在最重要的：

> **宁可明确失败，不允许低置信度错误点击。**

---

# 第五阶段：再加入 Tier 0 Corrections

我会把它放在 VLM 前面。

因为这个 ROI 很高。

结构：

```text
(URL pattern, target semantic key)
↓
历史 correction
```

例如：

```json
{
  "site": "automationexercise.com",
  "target_key": "cart_navigation",
  "locator": {
    "role": "link",
    "name": "Cart"
  },
  "successes": 12,
  "failures": 1,
  "consecutive_failures": 0,
  "enabled": true
}
```

执行：

```text
Correction hit
↓
Resolution Engine 验证
↓
成功 → success++
失败 → failure++
连续失败达到阈值 → disable
```

注意：

> correction 不能绕过 Resolver validation。

它只是：

```text
高优先级 candidate source
```

而不是：

```text
历史记录说点这里 → 无条件点击
```

这能形成真正的 learning loop。

```python
ObservedElement(
```

这样风险小很多。

# CDP node ID 的正确定位

如果以后用了 CDP，我会这样使用：

```text
backendDOMNodeId
```

只做：

### 同 session fast-path

```text

↓

↓
页面状态仍有效
↓
node still alive
↓

```

失败：


运行时 `target_ref` 可以不存在，只靠稳定 `target` replay。

# 补充：State-aware Grounding（第二轮评审，SauceDemo + AutomationExercise 双站点实证）

## 问题定性：state-grounding mismatch，不是 locator failure

两个独立站点复现同一模式：

```text
SauceDemo:
inventory state
├─ 点击商品名 → detail state（实际状态转移）
└─ 下一步却引用 inventory state 的 add-to-cart ref

AutomationExercise:
list state
├─ View Product → detail state
└─ 下一步却引用 list state 的 Add to cart（详情页是 button 不是 link）
```

统一抽象：

```text
S0
--action-->
S1

next target ∈ S0 而不是 S1
=> STATE_GROUNDING_MISMATCH
```

底层 locator 没坏——是 **Planner representation 不包含足够的 state identity**。

## 架构升级：插入两层

原路线图插入：

```text
ObservedElement
        ↓
Observation State Graph   ← 新增
        ↓
Planner refs-only
        ↓
State Grounding Validator  ← 新增
        ↓
LocatorSpec Compiler
        ↓
Resolver
```

- **Observation = 状态节点，用户操作 = 状态之间的边**（obs3 --click e17--> obs4）
- Planner 从**探索过的 transition graph** 选动作（from_state/action/target_ref/to_state）
- 代码 invariant（不靠 Prompt）：

```python
if step.target_ref.observation_id != current_observation_id:
    raise StateGroundingMismatch(...)
```

## 职责拆分（核心）

```text
Planner grounding: "想操作谁？"    → refs / transitions
Locator resolution: "DOM 里谁对应它？" → semantic resolver
```

当前问题根源：两者混在同一个 target/scope 生成里。

## 两个 grounding regression case（v2 验收标准）

```text
Regression 1 — SauceDemo:
进 detail 后，不得引用 inventory-only add-to-cart ref
→ 必须用 detail-state ref，或根本不进 detail（列表页直接加购）

Regression 2 — AutomationExercise:
进 product detail 后，target_ref 必须来自 detail observation
```

**验收**：执行前拒绝错误计划（STATE_GROUNDING_MISMATCH）即算成功；
第二阶段才做"mismatch → 按 transition graph 自动替换为当前 state 的对应 node"。

## 附加收益

1. Planner 优先选"系统真实观察过的动作"，不再按自然语言感觉构造 UI 路径
   （SauceDemo 案例：列表页直接 add-to-cart，根本不需要进 detail）
2. Preflight 的 candidate extraction / scope repair / goal anchor matching 等
   大量 repair 可大幅削薄——"ref 存在性 + 状态归属"由 validator 保证

## 执行建议

- 不修 SauceDemo Step 7 / AutomationExercise Step 9 本身——留作 grounding regression
- 下一条主线：**state-aware grounding**，不再修 Locator
